# 01.1 — LAN Drop v2: Self-Hosted Network Mode

LAN Drop originally depended on one simple condition: the Linux host and the client device had to already be connected to the same local network.

That model worked well.

LAN Drop v2 began with a different question:

> **What if the Linux host provided the network as well as the file-transfer service?**

Instead of relying on an existing router or Wi-Fi network, the Linux laptop creates its own wireless access point. Client devices connect directly to that network and access LAN Drop from there.

The result works, requires no additional hardware, and removes the dependency on an existing LAN.

It also turned out to be less convenient for normal everyday use.

That trade-off became the most interesting part of the experiment.

---

## Starting point

The original LAN Drop architecture depends on an existing network:

```text
                    EXISTING LOCAL NETWORK
                              │
                 ┌────────────┴────────────┐
                 │                         │
            Linux host                 Client
                 │                         │
                 │                         │
          LAN Drop :8080          Browser access
```

This is a practical model.

If both devices are already connected to the same Wi-Fi network, the client only needs to open the LAN Drop address and transfer files.

The infrastructure dependency is:

```text
LAN Drop
    │
    ▼
existing Wi-Fi / LAN
```

V2 explored removing that dependency entirely.

---

## The idea

The Linux host already runs:

- the Flask application
- the LAN Drop systemd service
- the file storage
- HTTPS
- authentication

The question was whether it could also provide:

- the wireless network
- local addressing
- client connectivity

The target architecture became:

```text
               Linux laptop
          ┌─────────────────────┐
          │                     │
          │   Wi-Fi Access Point│
          │   SSID: LAN-Drop    │
          │                     │
          │   LAN Drop service  │
          │                     │
          └──────────┬──────────┘
                     │
                   Wi-Fi
                     │
                     ▼
                  Client
```

No router would sit between the host and the client.

No Internet connection would be required.

---

## Checking the Wi-Fi hardware

Before attempting the hotspot, the Linux Wi-Fi adapter was checked using:

```bash
iw list
```

The adapter reported the following supported interface modes:

```text
Supported interface modes:
    * IBSS
    * managed
    * AP
    * AP/VLAN
    * monitor
    * mesh point
    * P2P-client
    * P2P-GO
    * outside context of a BSS
```

The important entry for this experiment was:

```text
* AP
```

This confirmed that the existing wireless adapter and Linux driver supported access-point mode.

No additional Wi-Fi adapter or router was required.

The active wireless interface was:

```text
wlp2s0
```

Before V2, it normally operated in:

```text
type managed
```

mode as a normal Wi-Fi client.

---

## Creating the LAN Drop network

NetworkManager was used to create the hotspot.

The initial proof-of-concept command was:

```bash
nmcli device wifi hotspot ifname wlp2s0 con-name LAN-Drop ssid LAN-Drop password "<password>"
```

This created a persistent NetworkManager connection profile named:

```text
LAN-Drop
```

The profile was later inspected with:

```bash
nmcli connection show LAN-Drop
```

The relevant configuration was:

```text
802-11-wireless.ssid: LAN-Drop
802-11-wireless.mode: ap
connection.interface-name: wlp2s0
connection.autoconnect: no
```

A shorter query confirmed:

```bash
nmcli -g 802-11-wireless.mode,802-11-wireless.ssid,ipv4.method,ipv4.addresses connection show LAN-Drop
```

with:

```text
ap
LAN-Drop
shared
```

`autoconnect` remains disabled intentionally.

The hotspot should only exist when LAN Drop is explicitly started.

---

## NetworkManager shared mode

When the hotspot became active, NetworkManager configured the Linux host with:

```text
10.42.0.1/24
```

on `wlp2s0`.

This was verified with:

```bash
ip -4 addr show wlp2s0
```

which reported:

```text
inet 10.42.0.1/24
```

The Linux machine now had two responsibilities:

```text
Linux host
   │
   ├── network provider
   │
   └── application server
```

A phone could see the new wireless network:

```text
LAN-Drop
```

and connect directly to it.

The phone correctly reported that the network had no Internet connection.

That was expected.

Internet access is not required for LAN Drop.

---

## Proof of concept

Once the phone was connected to the new `LAN-Drop` Wi-Fi network, the existing LAN Drop systemd service was started.

The application became reachable at:

```text
https://10.42.0.1:8080
```

The browser successfully loaded the existing LAN Drop interface.

A real file download was then performed from the Linux host to the phone.

The transfer succeeded.

This proved the complete path:

```text
Linux laptop
    │
    ├── creates Wi-Fi network
    │
    ├── receives 10.42.0.1
    │
    ├── runs LAN Drop
    │
    ▼
LAN-Drop Wi-Fi
    │
    ▼
phone
    │
    ▼
https://10.42.0.1:8080
    │
    ▼
upload / download
```

The proof of concept therefore worked with:

```text
external router     NO
Internet            NO
additional hardware NO
existing LAN        NO
```

The Linux laptop itself provided everything required for the transfer.

---

## V2 architecture

The final V2 network model is:

```text
                    LAN DROP v2

             Linux Mint laptop
        ┌─────────────────────────┐
        │                         │
        │ wlp2s0                  │
        │        │                │
        │        ▼                │
        │  Wi-Fi Access Point     │
        │                         │
        │  SSID: LAN-Drop         │
        │  IP:   10.42.0.1        │
        │                         │
        │  lan-drop.service       │
        │        │                │
        │        ▼                │
        │  Flask / HTTPS :8080    │
        │                         │
        └────────────┬────────────┘
                     │
                   Wi-Fi
                     │
                     ▼
                  Client
                     │
                     ▼
          https://10.42.0.1:8080
```

In V1, LAN Drop exists **inside** an existing LAN.

In V2, LAN Drop creates the LAN it needs.

---

## The launcher

The proof of concept initially required separate commands to:

1. activate the hotspot
2. start the LAN Drop service
3. inspect their status
4. stop the service
5. deactivate the hotspot

That worked, but was unnecessarily repetitive.

A small Bash launcher was therefore added:

```text
lan-drop
```

It coordinates NetworkManager and the existing systemd service.

The launcher supports:

```bash
lan-drop start
lan-drop stop
lan-drop status
```

The application itself was not rewritten.

The existing `lan-drop.service` remains responsible for running the Flask application.

The new launcher only coordinates the surrounding network state.

This keeps the two responsibilities separate:

```text
lan-drop.service
      │
      └── application lifecycle

lan-drop launcher
      │
      ├── hotspot lifecycle
      └── service control
```

---

## `lan-drop start`

Running:

```bash
lan-drop start
```

activates the saved NetworkManager profile:

```text
LAN-Drop
```

and starts:

```text
lan-drop.service
```

A successful start reports:

```text
Starting LAN-Drop...
Hotspot ready.

LAN-Drop is ready.
Wi-Fi : LAN-Drop
URL   : https://10.42.0.1:8080
```

The client can then:

1. connect to the `LAN-Drop` Wi-Fi network
2. open `https://10.42.0.1:8080`
3. upload or download files

---

## `lan-drop stop`

Running:

```bash
lan-drop stop
```

stops the application service and deactivates the hotspot.

The sequence is:

```text
LAN Drop service
      │
      ▼
stopped
      │
      ▼
LAN-Drop hotspot
      │
      ▼
deactivated
```

After the hotspot is disabled, NetworkManager automatically reconnects the Linux laptop to an available saved Wi-Fi network.

No home-network SSID is hard-coded into the launcher.

That behavior is left to NetworkManager.

This keeps the launcher portable across different normal Wi-Fi networks.

---

## `lan-drop status`

Running:

```bash
lan-drop status
```

checks the network and application separately.

Example while V2 is running:

```text
=== Hotspot ===
LAN-Drop  wifi  wlp2s0

=== Service ===
active
```

Example while it is stopped:

```text
=== Hotspot ===
Hotspot inactive

=== Service ===
inactive
```

This makes an important distinction visible:

```text
network state ≠ application state
```

LAN Drop v2 consists of both.

---

## Making the launcher a normal shell command

The launcher was initially executed from the project directory as:

```bash
./lan-drop start
```

To make it available from anywhere on the Linux system, a symbolic link was created:

```bash
sudo ln -s ~/lan-drop/lan-drop /usr/local/bin/lan-drop
```

After that, the launcher could be called from any directory:

```bash
lan-drop start
lan-drop status
lan-drop stop
```

The symbolic link points back to the working script rather than maintaining a second copy.

Changes to the original launcher therefore remain reflected in the command available through `/usr/local/bin`.

## SSH behavior

V2 exposed an important consequence of using a single Wi-Fi adapter.

Under normal conditions:

```text
Windows PC
    │
    │ existing Wi-Fi
    ▼
router
    │
    ▼
Linux laptop
    │
    ▼
SSH
```

The Linux adapter is operating in normal client mode.

When:

```bash
lan-drop start
```

is executed, the same adapter changes role:

```text
wlp2s0

managed
   │
   ▼
AP
```

The Linux host therefore leaves the existing Wi-Fi network and begins broadcasting `LAN-Drop`.

An SSH session reaching the laptop through the previous Wi-Fi network loses connectivity.

This is expected behavior, not a failure in SSH or LAN Drop.

The machine has deliberately left that network.

When:

```bash
lan-drop stop
```

is executed locally, the hotspot is deactivated.

NetworkManager reconnects the laptop to its saved Wi-Fi network, after which SSH becomes reachable again.

Depending on the SSH client, this can appear as if the connection has automatically recovered or reconnected.

This behavior demonstrated a practical consequence of changing the role of a physical network interface while remote administration depends on that same interface.

---

## V1 vs V2

The architectural difference is simple.

### V1

```text
                Existing Wi-Fi
                     │
          ┌──────────┴──────────┐
          │                     │
      Linux host             Client
          │
      LAN Drop
```

The network already exists.

LAN Drop only provides the application.

### V2

```text
                  Linux host
             ┌─────────────────┐
             │                 │
             │  Wi-Fi network  │
             │       +         │
             │    LAN Drop     │
             │                 │
             └────────┬────────┘
                      │
                      ▼
                   Client
```

The host provides both the network and the application.

That makes V2 more self-contained.

It does not automatically make it better.

---

## Was V2 actually better?

Not necessarily.

This became the most important conclusion of the experiment.

At first, removing the dependency on an existing LAN appeared to be a straightforward improvement.

Technically, it was.

LAN Drop could now operate without:

- a home router
- an existing Wi-Fi network
- Internet access
- additional network hardware

But once the system was actually used, the user workflow became worse.

### Normal V1 workflow

A user already connected to the local Wi-Fi can:

```text
open LAN Drop
      │
      ▼
transfer file
```

There is almost no network interaction required from the user.

### V2 workflow

The same user must now:

```text
leave current Wi-Fi
        │
        ▼
connect to LAN-Drop
        │
        ▼
open 10.42.0.1:8080
        │
        ▼
transfer files
        │
        ▼
leave LAN-Drop
        │
        ▼
reconnect to previous Wi-Fi
```

For the common case where a usable LAN already exists, this is clearly less convenient.

V2 removes infrastructure dependency at the cost of adding interaction for the user.

---

## Deliberate overengineering

In practical everyday terms, V2 is somewhat overengineered.

It successfully solves a problem that usually does not need solving.

If both devices already have access to the same Wi-Fi network, V1 offers the more direct workflow.

The existence of a technically more independent architecture does not change that.

The interesting result is therefore not:

> V2 is better because it removes the router.

The more accurate conclusion is:

> V2 demonstrates that the router can be removed, but doing so often makes the actual user experience worse.

This distinction matters.

Engineering improvements cannot be evaluated only by counting removed dependencies or added technical capabilities.

A system can become:

```text
more self-contained
more technically independent
more architecturally interesting
```

while simultaneously becoming:

```text
less convenient
less direct
less useful in the common case
```

LAN Drop v2 is a small example of that trade-off.

---

## Why keep V2?

Despite the usability regression, V2 remains valuable.

The purpose of keeping it is not to pretend that it replaced V1.

It did not.

The original LAN Drop remains the preferred mode when an existing LAN is available.

V2 is useful because it demonstrated several things directly:

- a Linux Wi-Fi adapter switching from managed mode to AP mode
- NetworkManager creating and managing a local wireless network
- the Linux host receiving a predictable local address
- client connectivity without a router
- application availability over the newly created network
- the relationship between physical interface state and SSH connectivity
- coordination between NetworkManager and systemd
- creation of a small Bash lifecycle wrapper
- use of `/usr/local/bin` and symbolic links for a custom command
- the difference between infrastructure independence and usability

Most importantly, the experimental part emerged from a working project rather than being an isolated networking exercise.

The sequence was:

```text
working application
        │
        ▼
new architectural idea
        │
        ▼
working prototype
        │
        ▼
real usage
        │
        ▼
observed trade-off
        │
        ▼
engineering conclusion
```

That is the reason V2 remains part of the project history.

## Final result

LAN Drop now has two useful operating models.

### V1 — Existing LAN mode

Use the network that already exists.

```text
existing LAN
     │
     ├── Linux host
     │      │
     │   LAN Drop
     │
     └── client
```

This remains the preferred mode for ordinary use.

### V2 — Self-hosted network mode

Let the Linux host create the network.

```text
Linux host
    │
    ├── LAN-Drop Wi-Fi
    │
    └── LAN Drop service
             │
             ▼
           client
```

This mode is independent of external network infrastructure.

It is technically successful, but usually less convenient.

The experiment therefore ended with a useful engineering lesson:

> **Removing a dependency does not automatically improve a system.**

LAN Drop v2 made the system more independent.

LAN Drop v1 remains more practical.

Both results are worth keeping.
